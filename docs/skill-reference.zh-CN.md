# Reuse Before Build 中文参考

## 一句话说明

在开始写新代码之前，先确认是否已经存在成熟、可靠、可维护的解决方案。

## 为什么需要这个 skill

AI 很容易直接开始实现，因为写代码是它最自然的动作。但在真实软件工程里，直接自研并不总是最好的选择。

很多“看起来应该自己写”的东西，实际上已经有成熟的开源库、商业服务、官方 API、内部工具或框架能力可以复用。先检查这些选项，可以减少代码量、降低维护成本，并避免把项目带入不必要的复杂度。

## 应该检查哪些方案

- 项目内部是否已经有类似模块、工具、组件或服务。
- 团队或公司内部是否已有平台能力、基础设施或共享库。
- 官方 API、SDK、框架能力是否已经覆盖需求。
- 主流开源项目是否成熟、维护活跃、社区可靠。
- 商业产品或托管服务是否更合适。
- 是否可以轻量改造现有方案，而不是完整自研。

## 如何比较方案

比较时不要只看“能不能用”，还要看：

- 功能匹配度
- 成熟度和维护状态
- 安全风险
- License 和合规风险
- 成本
- 接入复杂度
- 长期维护成本
- 厂商锁定或生态锁定
- 对当前架构的影响

## 推荐决策顺序

1. 能直接复用成熟方案，就直接复用。
2. 不能直接复用，但可以低成本改造，就改造。
3. 如果商业服务明显更稳定、更便宜或更快，就考虑购买。
4. 只有在以上方案都不合适时，才自研。

## AI 的标准输出格式

在开始自定义实现前，AI 应该先给出：

```md
Existing options checked:
- ...

Recommendation:
- Reuse / Adapt / Buy / Build

Reason:
- ...

Risks or tradeoffs:
- ...
```

中文表达可以是：

```md
已检查的现有方案：
- ...

建议：
- 复用 / 改造 / 购买 / 自研

理由：
- ...

主要风险或取舍：
- ...
```

## 什么时候可以跳过

- 任务非常小，例如改一个文案、修一个明显 bug、调整一个局部样式。
- 用户明确要求自研。
- 项目有明确约束，不允许引入外部依赖或商业服务。
- 已经在当前上下文中完成过同类方案评估。

## 最重要的判断

不要为了“看起来更完整”而增加复杂度。这个 skill 的目标不是阻止自研，而是让自研变成一个经过判断的选择。
